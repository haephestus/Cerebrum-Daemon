## 3. Note chunk annotation brought to file-pipeline parity (rich metadata + accurate byte offsets)

**What.** The note chunker's `.md` `CHUNK_START` comment was a lean one-liner
(`chunk_index`/`page`/`fingerprint`); it now emits the **full multi-line block**
the file pipeline uses — `chunk_fingerprint`, `chunk_type`, `chunk_index`,
`source_block_ids`, `parent_chunk_index`, `token_count`, `byte_start`, `byte_end`,
`pdf_page_start/end` — **plus a note-specific `page_id` line**.

**Why.** Uniform artifacts across the note and file (textbook/paper/article)
pipelines, and byte offsets that live in the annotation like the file format.
`byte_start`/`byte_end` are **content-relative** (they point past the comment)
and **zero-padded to a fixed width**, the same trick `markdown_handler` uses so
the comment's length is independent of the offset values it carries. Nothing was
ever lost from the DB — the `note_chunks` registry already held all of this — but
the artifact now matches.

**Files.**
- `notes/note_util_inator.py` — `NoteChunkerInator.chunk_note`: rich fixed-width
  `_meta()` annotation; registry + Document metadata now also carry
  `chunk_type`/`byte_start`/`byte_end`.
- `notes/chunk_analyser_inator.py` — `chunk_stream_inator`: the annotation-strip
  now only fires when the fetched slice **starts with** `<!-- CHUNK_START` (old
  annotation-inclusive chunks), so content-only text containing `-->` (arrows,
  code) is never truncated.

**Note.** The **file pipeline (`FileMarkdownChunker.chunk_markdown`) was
untouched** — this only lifts the note chunker to the same format. Old notes keep
fetching correctly (the strip guard handles them); re-chunk a note to regenerate
its `.md` in the rich format.

**Verified.** In-process: `md.encode()[byte_start:byte_end] == chunk text` for
every chunk across 4 chunks / 2 pages (zero mismatches, `chunk_index`
contiguous); all rich fields + `page_id` present in the emitted `.md`; strip
guard preserves content-only text containing `-->`. Both files compile + import.

## 2. Per-page analysis is now the canonical output; display routes read from the page folders

**What.** Chunk analysis was assembled note-level (a flat `chunk_diagnostics`
list keyed by a **global** `chunk_index`, overview taken from "the last chunk",
full excerpt duplicated onto every finding). It's now written **per page** as the
canonical store, and the display routes read it back.

Per-page `pages/<page_id>/analysis.json`:
```
{ page_id, note_id, content_version, cached_at,
  chunks: [ { chunk_id: "<page_id>-chunk<local>", chunk_index: <global>,
              chunk_excerpt, findings: [...] } ],
  page_overview }
```
`chunk_id` is **page-scoped** (display), `chunk_index` is kept for registry
joins, the excerpt is stored **once per chunk**, and the note-level overview goes
to `manifest.json`.

**Why.** Matches the intended per-page design and finishes the two
`cache_inator.py` TODOs ("redirect the analysis cache to pages", "overview from
manifest") on the read side.

**Files.**
- `cerebrum_core/learning_center_inator.py` — `_run_chunk_analysis`: builds the
  per-page structure (page-scoped ids, excerpt-once, flattened findings) and
  writes it via `write_page_analysis`; overview → manifest.
- `api/routes_learning_center.py` — new `_collect_page_analyses` reader; `GET
  /fetch/analysis` and `/fetch/analysis/full` now read the page files + manifest
  overview, rebuilding the **exact client response contract**; `_attach_block_refs`
  joins on `chunk_index` (not a regex over `chunk_id`, which `p1-chunk0` broke).

**Note.** The analyser's `note_analysis_dir/chunk_N.json` cache stays as the
**internal** fingerprint-skip cache (keyed by global `chunk_index`); it is no
longer what the client reads. Re-chunk + re-analyse a note to populate the new
per-page files (its registry is otherwise the stale single-page state).

**Verified.** Compile + import clean; round-trip on a temp note (write new
per-page shape → `_collect_page_analyses`) produced page-scoped ids,
`chunk_index`, `page_id`, one-excerpt groups and the manifest overview — matching
the client's flattener keys exactly.

## 1. Swagger can send the daemon key (OpenAPI security schemes)

**What.** `/docs` now shows an **Authorize** button that injects
`X-Daemon-Key` (and offers a Bearer field) on every "Try it out" — previously
Swagger had no security scheme, so every call 401'd on the auth middleware.

**Why.** Test/admin routes (e.g. `POST /test/chunkinator`) are gated by
`DaemonAuthMiddleware`, but Swagger won't attach the header unless it's declared
as a security scheme. No auth behaviour changed — the middleware still validates
exactly as before; Swagger just knows how to send it now.

**Files.**
- `cerebrum_inator.py` — `create_api_server`: custom `app.openapi()` adds
  `DaemonKey` (apiKey header `X-Daemon-Key`) + `BearerAuth` (http bearer) schemes,
  with `DaemonKey` as the global security requirement.

**Verified.** With routers loaded, the generated schema carries both security
schemes + global `DaemonKey` security and all `/test/*` paths; `py_compile` OK.
