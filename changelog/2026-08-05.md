## 7. Analysis completion path: topic assignment + vectorstore analysis cache

**What.** When a note's analysis completes, it now (1) assigns the note's
topic from the overview via the topic entity, and (2) persists the completed
analysis (overview + findings) into a queryable per-note vector store.

**Why.** Notes are registered with no topic; analysis *determined* the topic
(`note_overview.topic`) but nothing wrote it back — `create_note` (the only
topic writer) was never called, so `notes.topic`/`topic_id` stayed empty and
all topic grouping (mastery/engrams/planner) ran on blanks. Also formalises
the intended two-tier analysis lifecycle: **current** = version-keyed JSON,
**historical** = vectorstore (queryable for overview development).

**Files.**
- `database/note_engram_repository/notes.py` — new `assign_note_topic(note_id, topic)`: resolves the topic entity and sets `notes.topic` + `notes.topic_id` (resolves before taking the non-reentrant write lock).
- `utils/cache_inator.py` — new `AnalysisVectorCacheInator` (+ `CacheType.ANALYSIS_VECTOR`, registered in `make_cache`): persists overview + per-finding docs, versioned, to `note_analysis_dir/analysis_history/`; `.semantic()` / `.history()` for querying.
- `learning_center_inator.py` — `_run_chunk_analysis` now calls new `_finalise_analysis()` (best-effort) which does topic assignment + history persistence.

**Verified.** Compile + full-app import; `register_inator` (no topic) → `assign_note_topic` sets topic + id, variant spellings dedupe to one topic, missing note/blank topic → `None`; overview-text builder embeds key fields. (FAISS `persist()` needs a live embedder, so exercised only for construction + graceful failure.)

**Open.** `active_analysis` still runs as a background task whose result the route discards, and `mark_analysis_status(..., "done")` isn't called after it — the analysis *status* lifecycle is still incomplete (topic/history now fire regardless, inside `_run_chunk_analysis`).

## 6. Fix: existing-DB open crashed on `topic_id` index (from change-set 5)

**What.** Moved the two `topic_id` indexes out of `SCHEMA_SQL` into migration
`0002`.

**Why.** `executescript(SCHEMA_SQL)` runs before migrations. On an existing DB
`CREATE TABLE IF NOT EXISTS notes` is a no-op (no `topic_id` column yet), so
`CREATE INDEX ... ON notes(topic_id)` in `SCHEMA_SQL` raised
`sqlite3.OperationalError: no such column: topic_id` at startup. The migration
adds the column first, then the index.

**Files.**
- `database/note_engram_repository/schema.py` — removed the two `topic_id` indexes (comment explains why they live in the migration).
- `database/note_engram_repository/migrations.py` — migration `0002` now creates `idx_notes_topic_id` / `idx_topic_mastery_topic_id` after the `ALTER ADD COLUMN`.

**Verified.** Simulated a realistic pre-topic DB → `NoteEngramRepository()` opens without error, columns + indexes added, backfill linked rows, idempotent on re-open.

## 5. Topic entity (stringly-typed topic → first-class identity)

**What.** Introduced a `topics` table (per-user, slug-unique) as the topic
entity; `notes.topic_id` and `topic_mastery.topic_id` reference it; all topic
lookups/writes go through identity; backfill migration for existing data.

**Why.** `topic` was a free-text key that engrams/mastery grouped on and the
planner cross-DB-joined on, so two spellings of the same subject fragmented a
student's mastery. The entity gives a stable id, canonical-slug dedup, and
id-stable renames.

**Files.**
- `utils/topic_inator.py` — added `topic_slug()` (casefold identity key).
- `engrams/core/types.py` — `TopicMastery.topic_id`.
- `database/note_engram_repository/schema.py` — `topics` table; `topic_id` on `notes` + `topic_mastery`.
- `database/note_engram_repository/topics.py` — new `TopicsMixin`: `resolve_topic`, `_lookup_topic_id`, `get_topic`, `list_topics`, `rename_topic` (id-stable, propagates name).
- `database/note_engram_repository/__init__.py` — registered `TopicsMixin`.
- `database/note_engram_repository/notes.py` — `create_note` resolves topic → id + canonical name.
- `database/note_engram_repository/mastery.py` — `get_topic_masteries` / `get_topic_mastery` / `upsert_topic_mastery` are id-aware.
- `database/note_engram_repository/engrams.py` — `get_topic_engrams` groups on `topic_id`.
- `database/note_engram_repository/attempts.py` — `get_topic_activity_since` matches on `topic_id`.
- `engrams/core/mastery_service.py` — `recompute_topic_mastery` stamps `topic_id`; `resolve_topic` added to `MasteryRepository` ABC.
- `database/note_engram_repository/migrations.py` — migration `0002` backfills topics + links (collapses spelling variants).

**Verified.** Fresh DB: variant spellings → one topic; grouping by any casing finds all; rename id-stable + names propagated, mastery intact. Legacy DB: backfill collapsed variants and linked `topic_mastery`.

## 4. "Resolve all" — architecture-review cleanup program

Several cross-cutting fixes from the architecture review, plus the cache/vector
unification directive.

### 4a. Unified embeddings + vector store + flexible cache
**Why.** 6 ad-hoc `OllamaEmbeddings(...)` sites; the grading `VectorStore` was
abstract with no implementation; three near-duplicate cache classes. Cache
constraints: keep the same files, sit on top of the vector store, support
flexible cache types.
- `utils/embeddings_inator.py` — new `get_embeddings()` (single client cache).
- `utils/vector_store_inator.py` — new `FaissVectorStore` (the one concrete store).
- `utils/cache_inator.py` — `CacheType` + `VectorCache` + `make_cache`; retrieval/engram caches became thin shims over `VectorCache` (same paths/method names).
- Refactored embedding sites: `knowledgebase_inator.py`, `utils/archive_inator.py`, `utils/retrieve_inator.py`, `utils/chunk_analyser_inator.py`.

### 4b. Cloud/local toggle bug fix
**Why.** `study_planner` read `models.use_cloud` (doesn't exist → always local) and `ai_grading` read `ollama.prefer_cloud` (doesn't exist → always cloud); the real field is `ollama.toggle_cloud`. The toggle was silently ignored.
- `user_inator.py` — new `should_use_cloud()` (reads `toggle_cloud` + API-key gate).
- `study_planner_inator.py`, `engrams/grading/ai_grading.py` — use it.

### 4c. Schema typos + migration runner
- `database/note_engram_repository/schema.py` — `target_congnitive_level → target_cognitive_level`; `attempts TEXT → INTEGER`.
- `database/note_engram_repository/generation_queue.py`, `learning_center_inator.py` — updated readers.
- `database/note_engram_repository/migrations.py` — new lightweight, tracked migration runner (migration `0001` renames the typo column on existing DBs); wired into `_base._ensure_schema`.

### 4d. Deleted dead legacy repository
- Removed `engrams/storage/sqlite_repository.py` (1994 lines, referenced only in comments).

### 4e. Atomic `submit_*` writes
**Why.** Submitting an attempt was 3 separate commits (attempt + responses + job); a crash orphaned rows.
- `database/note_engram_repository/_base.py` — `_transaction()` context manager.
- `database/note_engram_repository/attempts.py` — `record_short_question_submission` / `record_long_question_submission` (one transaction).
- `engrams/core/mastery_service.py` — `submit_short_question` / `submit_long_question` use them; ABC updated.

### 4f. Grading worker wired into lifespan
- `cerebrum_inator.py` — `run_worker` started alongside the generation worker (runs without a concrete answer vector store; note-context is concrete, answer-store ops gated).

### 4g. Topic normalization (pre-entity, non-breaking)
- `utils/topic_inator.py` — new `normalize_topic()`; applied at note-write boundary.

**Verified.** Compile + full-app import; SQLite smoke tests for migration runner, atomic commit + rollback, config resolver, topic normalizer, cache factory; cached→KB retriever fallback cases.

## 2. Short-question grading: async, mirroring long_question

**What.** Converted open-response short-question submissions from a broken
synchronous exact-match path to async AI grading, mirroring long_question.

**Why.** Short questions became open-response (free-text `expected_answer`),
but the response/scoring path still assumed lettered MCQ answers — and the
route already passed `{question_id, raw_answer}`, so `process_short_question_
attempt` did `r["selected_option"]` → `KeyError`. The path couldn't run.

**Files.**
- `database/note_engram_repository/schema.py` — reshaped `short_question_responses` (raw_answer + gradable fields).
- `engrams/core/types.py` — `QuizResponse` open-response; `ShortAnswerGrade` / `ShortQuestionGradingResult`.
- `database/note_engram_repository/attempts.py` — save/read/grade for the new shape.
- `engrams/core/scoring.py` — `score_short_question` averages AI per-question scores.
- `database/note_engram_repository/grading_jobs.py` — `get_short_question_grading_context`.
- `engrams/grading/ai_grading.py` — short-question grading schema/prompt/parser/pipeline; `call_grading_model` takes a schema override.
- `engrams/core/mastery_service.py` — `submit_short_question` (async) + `apply_short_question_grading_result`; ABC updates.
- `engrams/grading/worker.py` — type-aware hydrate/process (long + short).
- `learning_center_inator.py` — `submit_short_question_answers` returns `(attempt_id, job_id)`.
- `api/routes_learning_center.py` — route returns `pending_grading`; `{question_index, raw_answer}` model.

**Verified.** Compile + import; ABC satisfied; parser desync-resistance; SQLite round-trip (submit → grade → read-back).
