Paths are relative to `src/`. Change-sets are ordered newest first.

Theme for the day: make engram answering **offline-first friendly** for the
client — accept client-minted attempt identity so a queued offline submit can be
replayed idempotently, and record the student's real (offline) answer time so it
drives mastery ordering.

## 1. Accept client-minted `attempt_id` + `attempted_at` on submit; idempotent attempts

**What.** The four engram submit endpoints now accept optional `attempt_id` and
`attempted_at`. When the client supplies them (offline-first: the app mints a
nanoid-shaped id per attempt and stamps the offline answer time), the daemon uses
them verbatim; otherwise it falls back to its own `_nanoid()` / now, so existing
callers are unaffected. Attempt inserts are now idempotent on the id, and a
replayed submit does not enqueue a duplicate grading job.

**Why.** The client queues answers made offline and replays them on reconnect.
Without a stable client id, a replay recorded a **duplicate** attempt (and, for
short/long, a duplicate LLM grading job). Client-owned attempt identity makes the
replay a no-op; the client's `attempted_at` (not server-receive time) then orders
`get_recent_attempt_scores`, so mastery reflects when the student actually
answered. Attempts stay client-owned raw facts; mastery stays daemon-derived.

**Files.**
- `api/routes_learning_center.py` — `MCQSubmission` / `FlashcardSubmission` /
  `ShortQuestionSubmission` / `LongQuestionSubmission` gain optional
  `attempt_id` + `attempted_at`; the four submit handlers pass them through.
- `cerebrum_core/learning_center_inator.py` — `submit_mcq_answer` /
  `submit_flashcard_rating` / `submit_short_question_answers` /
  `submit_long_question_answer` thread the two params.
- `cerebrum_core/engrams/core/mastery_service.py` — `process_mcq_attempt` /
  `process_flashcard_attempt` / `submit_short_question` / `submit_long_question`
  use `attempt_id or _nanoid()` and `attempted_at or _now()`; `MasteryRepository.
  create_attempt` return type is now `bool`.
- `database/note_engram_repository/attempts.py` — `create_attempt` and
  `_insert_attempt` are `INSERT OR IGNORE` returning "inserted?"; new
  `_existing_job_id`; `record_short_question_submission` /
  `record_long_question_submission` skip response/job inserts and return the
  existing job id when the attempt already existed.

**Compatibility.** `attempt_id` becoming client-mintable means the
`engram_attempts.id` column now holds either a server nanoid or a client-supplied
id — both are opaque unique strings. No schema/migration change.

**Note (client side, separate repo).** The Flutter client mints `attempt_id` via
a `uuid4().hex`-shaped nanoid and sends `attempted_at`; it also fetches engrams
with `include_answers=true` to enable offline answer comparison (client-gated
reveal after submit). MCQ answers (`correct_option`) remain stripped from the
default student list — the client opts into answers explicitly.

**Verified.** `python -m py_compile` clean on all four changed modules.
Live end-to-end (offline queue → reconnect replay dedup) needs a running daemon +
client.
